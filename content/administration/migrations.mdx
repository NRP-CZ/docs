# Migrations & Updates

<MigrationHeader
  date="2026-11-19"
  title="oarepo-app 6.0.0 → 8.0.1"
  versionBadge="oarepo-app ≥ 8.0.1"
/>

This upgrade moves the repository to InvenioRDM 14.0.6 and changes repository configuration, workflow permissions, model presets and UI components. Existing repositories also need a database migration and a search index rebuild. Repositories with legacy CCMM data need to convert vocabulary references in published records and drafts.

<MigrationAffected>

| Affected | Not affected |
|----------|--------------|
| Repositories upgrading from `oarepo-app 6.0.0` to `8.0.1` | New repositories created with `oarepo-app 8.0.1` |
| Repositories with legacy CCMM vocabularies or records and drafts that reference them (step 7) | Repositories without legacy CCMM data (step 7) |
| Repositories using e-INFRA login (step 4) | Repositories without e-INFRA login (step 4) |

</MigrationAffected>

<MigrationSteps>

**1. Update `pyproject.toml` and check the deployment**

Pin `oarepo-app` to `8.0.1` and keep the extras used by your repository. This is the dependency for a repository using the production and CCMM extras.

```toml filename="pyproject.toml"
dependencies = [
    "oarepo-app[production,ccmm]==8.0.1",
]
```

Keep the other repository dependencies, including `oarepo[s3,rdm]` if already declared. The upgrade still requires Python 3.14. Ensure that your deployment image includes Pango for the new WeasyPrint dependency. If you use GlitchTip, include `oarepo-glitchtip` in the environment before calling `config.initialize_glitchtip()`. Update custom Sentry code to use the `sentry-sdk` 2.x API.

Compare your Invenio template overrides, React overridables and configuration keys with the versions resolved in `uv.lock`. This upgrade includes major updates to `invenio-rdm-records`, `invenio-communities`, `invenio-requests`, `invenio-vocabularies`, `invenio-users-resources`, `invenio-jobs` and `invenio-checks`. Check compatibility if your application uses `oauthlib` (now 4.x), `cryptography`, `pillow`, `pikepdf` or `simplejson` directly. OARepo also adds optional `llm`, `ark` and `antivirus` extras, each with a `-development` variant.

**2. Update `invenio.cfg`**

Move configuration helper imports to `oarepo_config`. Repositories that already moved these imports in the 6.3.0 migration can keep them.

```python filename="invenio.cfg"
# Before
from oarepo import config
from oarepo_app.config import CommunityWorkflow, IndividualWorkflow, configure_workflows

# After
import oarepo_config as config
from oarepo_config import CommunityWorkflow, IndividualWorkflow, configure_workflows
```

- Pass your existing `languages=` explicitly to both `configure_generic_parameters` and `configure_ui`. The default changed to English. For a Czech repository, use `languages=(("cs", "Czech"),)` in both calls.
- Import symbols such as `is_vedidk` and `ExternalLinkConfig` from `oarepo.initial_rdm_config`.
- Move draft actions from `OAREPO_UI_DRAFT_ACTIONS` into `OAREPO_UI_RECORD_ACTIONS`. Replace any use of `COMMUNITIES_RECORDS_SEARCH_ALL` with `OAREPO_REQUESTS_DEFAULT_RECEIVER`.
- If you customise `NOTIFICATIONS_BUILDERS` or `NOTIFICATIONS_BACKENDS`, start with the package defaults and extend them explicitly. Assigning either setting now replaces its defaults.
- The legacy `/api/files` endpoint is disabled. `MAX_CONTENT_LENGTH` limits form-data request bodies, and streamed file uploads are exempt. Login and signup default to 10 requests per minute. Community and request errors now return HTTP 400 in cases that previously returned 500. Update clients or tests that depend on those responses.
- Review `REQUESTS_REVIEWERS_ENABLED`, which now defaults to `True`. The default vocabulary permission policy allows administrators to create and update items. Set `VOCABULARIES_PERMISSIONS_POLICY` explicitly if your repository needs different permissions.
- The DataCite provider and DOI PID configuration are added automatically unless you define a provider named `datacite`. Keep that provider name in custom `RDM_PERSISTENT_IDENTIFIER*` settings so they take precedence. The DOI form default changed from `not_needed` to `no`, and `/doi_settings` is served by the API app.

`oarepo_config` also provides `configure_detail_sidebar(templates=..., move=[...])`, `configure_files`, `configure_ark`, `configure_llm` and `configure_collections`. `configure_ui` accepts a `CSP` instance via `csp=`.

**3. Update workflows and model definitions**

- In `COMMUNITIES_ROLES`, set `can_curate=True` for each role that should review submissions. Invenio maps its built-in manager and curator roles to roles with `can_manage=True` and `can_curate=True`. These flags affect community invitations, membership and sub-community requests, record inclusion and submissions, and their notifications.
- Review `CommunityWorkflow`. The default `draft_creation_community_roles` now includes submitters, curators and owners. Both `read_restricted_community_roles` and `record_manage_community_roles` now default to curators and owners. Set explicit role lists if your repository needs the previous access rules. The default `can_manage_quota` now also allows user managers, and `can_manage_record_access` now also allows administrators.
- Replace `CompositeAndGenerator` with `RequireAll` and `CompositePermissionPolicyMixin` with `BooleanPermissionPolicyMixin`. The `RecordOwnerInRecordCommunity` and `RecordOwnerInDefaultRecordCommunity` generators require the latter mixin. Remove references to `UserInCommunityNeed`, `load_community_user_needs` and `AutoRequest`. Base custom generators on the Invenio classes.
- Update custom request code to accept `topic=` in receiver functions, remove `*args` from `can_create(...)` overrides and use `PublishRequestType.get_topic_type()`.
- For CCMM models, replace `ccmm_nma_preset_1_1_0` with `ccmm_preset_1_1_0` from `ccmm_invenio.models` and change `CCMMDataSet` references to `CCMMDataset`. The `ccmm_production_preset_1_1_0` alias still works. Update imports from the removed `ccmm_invenio.parsers`, `ccmm_invenio.serializers`, `ccmm_invenio.schemas` and `ccmm_invenio.conversion` modules. Store related identifiers in `metadata.related_resources` so that `metadata.related_identifiers` can be computed from them. Read `related_resources` in API clients that previously expected `related_identifiers` in the JSON export.
- For RDM models, load the `subjects` vocabulary and update fixtures and imports that use `RDMSubject`. Update custom validation or import code that assumes `RDMDate.date` is a single date. It now accepts EDTF dates and intervals. Import `oai_preset` from `oarepo_rdm.model.presets.oai`. Remove references to `RDMRecordSchemaMixin`, `ReviewMappingPreset`, `CommunitiesServiceConfigLinks`, `CommunityRecordsService` and the former community workflow, inclusion and access components.
- For `oarepo-model` customisations, review dependencies between customisations that relied on name order. The builder now orders them by what they modify. Create the target dictionary before using `AddToDictionary`. Check `AddFacetGroup` on models without drafts, where it may fail. Remove uses of `BuilderConstant`, `add_constant()` and `get_constant()`.
- Remove references to the two deleted media-files presets, `MediaFilesRecordServiceConfigPreset` and the `FileRecordServiceComponentsPreset` from `oarepo_model.presets.drafts.services.files.media_files_record_service_components`.
- In custom models, set `model:` on `pid-relation` fields and point EDTF interval range queries and facets at `<field>_range`. Replace the `multilingual-type` alias with `multilingual`. Replace uses of the removed `oarepo_runtime` schema fields `MultilingualField`, `I18nStrField` and their `*UIField` variants with the model datatypes `multilingual` or `i18ndict` as appropriate.

If your lockfile resolves `oarepo-requests` 11.0.0, check custom code that uses `proxies.current_oarepo_requests_resource`. The symbol is a plain function in that release, so code that accesses resource attributes directly through it fails.

**4. Update e-INFRA login**

Switch the login configuration to `configure_einfra_oidc`. The datarepo setup uses the eligible-entitlements parser.

```python filename="invenio.cfg"
from oarepo_oidc_einfra.remote import einfra_eligible_parser_factory

config.configure_einfra_oidc(entitlements_parser=einfra_eligible_parser_factory())
```

If you configure the parser directly, replace `EINFRA_COMMUNITIES_ROLES_TRANSFORMER` with `EINFRA_ENTITLEMENTS_PARSER` and adapt your callable to the new signature. The parser runs at login. If you assemble an `EINFRA` dictionary from environment settings, check its keys against the new configuration. `EINFRA_LOGIN_APP` is still supported.

Remove Perun synchronisation tasks from the Celery beat schedule and any uses of the old `invenio einfra` CLI, AAI invitation request type or invitation links. The Perun integration is now read-only and manages repository roles and memberships based on the entitlements read at login. Review grants from the old integration manually, since the new implementation can only revoke tracked grants.

**5. Update UI overrides and fixtures**

- Add `PermissionsComponent` if you build the record UI's component list from scratch. The RDM and CCMM base configurations already include it. Remove the old `record_detail_permissions` and `deposit_*_permissions` attributes. On edit and preview pages, use the draft permission names, such as `can_delete_draft`, `can_update_draft` and `can_draft_read_files`. Replace reads of `config.permissions` and `config.filesLocked` with values from `parseFormAppConfig()`, which reads the form's hidden inputs.
- Replace `VocabularySelectField`, `LocalVocabularySelectField`, `VocabularyTreeSelectField`, `VocabularyRemoteSelectField`, `VocabularyPickerField` and `useVocabularySuggestions` with `VocabularyField`. It queries the API and uses the `{id, title_l10n}` values at the corresponding path in the record's `ui` serialization. Remove `DepositVocabularyOptionsComponent` and migrate any custom JS that reads `form_config["vocabularies"]` to the new data sources.
- Update links from `oarepo_vocabularies_ui.edit` to `oarepo_vocabularies_ui.deposit_edit`. Move sidebar customisations that used `SidebarLink.jinja` to `OAREPO_VOCABULARIES_UI_SIDEBAR_TEMPLATES`.
- Update overrides of `<prefix>.TabForm.PublishButton` to accept the `record` prop. The button creates and submits a publish request when the workflow offers one.
- Community invitations now use the InvenioRDM UI. Remove references to `CommunityInvitationsModal` and compare your overrides of `details/members/base.html`, `details/members/invitations.html` and `details/settings/base.html` with the InvenioRDM templates. If you override `details/header.html`, check that your override exposes the new **Add sub-community** action where appropriate.
- Update identifier icon paths in templates and CSS from `/static/images/identifiers/<scheme>.svg` to `/static/images/<scheme>.svg`. Add `is_displayed(identity)` to custom exporters.
- For RDM and CCMM, update integrations that call the removed `citation` export to use the hidden `bibliography` export. For CCMM, replace `/export/datacite` with `/export/datacite-json` or `/export/datacite-xml`. CCMM XML is available as the `ccmm-xml` export and as `ccmm` in OAI-PMH. Update OAI-PMH consumers that use the removed DCAT format.
- For CCMM locations, include the Leaflet styles in your deposit and detail templates. Placement of the locations sidebar can be configured with `configure_detail_sidebar`, or disabled with `CCMM_INVENIO_LOCATIONS_SIDEBAR = False`.
- Update vocabulary IDs in fixtures and import data. The loader now discovers `oarepo.fixtures` entry points and `<model-code>.yaml`, `.json` or `.jsonl` files in `app_data`. Check that your registered entry points and files matching model codes contain data you intend to load.

**6. Rebuild assets and migrate the database**

For a disposable local instance, run `./run.sh reset` after updating your code and fixtures. This reinstalls the application, rebuilds assets and recreates the database and indices. Continue with step 8.

<Callout type="warning">
  `./run.sh reset` deletes local data. To preserve existing data, back up the database, rehearse the migration on a staging copy and pause writes and scheduled jobs during the production migration.
</Callout>

When testing with a copy of production data, configure the staging S3 bucket, `SECRET_KEY` and DOI credentials before starting the upgraded application.

Install the updated dependencies and rebuild the frontend assets, including the new webpack bundle from `oarepo-requests`. With the runner, `upgrade` also rebuilds the webpack bundles. In a container deployment, rebuild the application image with the updated dependencies and assets. Run the Alembic migration with the upgraded application against the existing database.

```bash
./run.sh upgrade
./run.sh invenio alembic upgrade
```

The migrations include the `einfra_user_entitlements` table, removal of the old AAI invitation requests and timezone-aware OAI-PMH harvest datestamps.

For existing CCMM records or drafts with manually entered identifiers stored only in `metadata.related_identifiers`, copy those relations into `metadata.related_resources` before the upgraded application next saves them. Keep existing related resources. Carry over the relation type and any resource type at the related-resource level, and put the identifier and scheme in that resource's `identifiers` list. Saving recalculates `metadata.related_identifiers` from the related resources. Plan this data conversion for your repository alongside the vocabulary migration in step 7.

Recreate the search indices and reindex all data. Record and draft mappings now come from `invenio-rdm-records`. Review custom index overrides for `version_id` (now `long`), EDTF intervals, PID relations, CCMM fields and subject references. Vocabulary indices gained `mappings` and `custom_fields`, and harvest records also need reindexing. Use the sequence below whenever step 7 calls for a rebuild. Repositories that skip step 7 run it once now.

```bash
./run.sh invenio index destroy --yes-i-know
./run.sh invenio index init
./run.sh invenio rdm-records custom-fields init
./run.sh invenio communities custom-fields init
./run.sh invenio rdm-records rebuild-index
./run.sh invenio rdm rebuild-all-indices
```

Use the upgraded Celery workers to process the indexing queue. Wait for reindexing to finish before proceeding to the next phase. See the [runner reference](/installation/run_script#index--manage-the-search-index).

**7. Migrate existing CCMM vocabularies and records**

Take `scripts/migration_vocabs.py` from the source of your target `ccmm-invenio` version and make it available in the repository as `scripts/migration_vocabs.py`. It updates vocabulary types and PID types (for example, `filetypes` → `fileformats` and `v-lan` → `lng`), loads the new vocabulary items and converts references such as SPDX licence IDs and COAR access rights in stored data. The script targets `datasets_metadata` and `datasets_draft_metadata`. Adapt its `TABLES` list to cover every CCMM model in your repository. See the [CCMM migration script and its command sequence](https://github.com/NRP-CZ/ccmm-invenio/blob/v2.0.2/scripts/migration_vocabs.py).

1. Mark legacy items, migrate the vocabulary types and load the new vocabularies in this order.

   ```bash
   ./run.sh invenio shell scripts/migration_vocabs.py mark
   ./run.sh invenio shell scripts/migration_vocabs.py migrate_types
   ./run.sh invenio shell scripts/migration_vocabs.py load
   ```

2. Rebuild the indices using step 6 and wait for indexing to finish.
3. Convert the vocabulary references in the stored records and drafts. The script also combines legacy start and end date pairs into EDTF intervals.

   ```bash
   ./run.sh invenio shell scripts/migration_vocabs.py migrate_data
   ```

4. Rebuild the indices again. Review any `cannot convert` messages and check that records and drafts resolve the new vocabulary items before removing deprecated entries.
5. Once those checks pass, remove the deprecated entries and rebuild the indices a final time.

   ```bash
   ./run.sh invenio shell scripts/migration_vocabs.py remove_deprecated
   ```

**8. Verify repository behaviour**

- Open existing records and drafts. Check search and facets, file access, vocabulary fields and the exports used by your repository.
- Test draft creation, publication and resubmission after declining, cancelling or expiring a community review. Each of these outcomes opens a new review for the same community. The workflow is set when the review is created. Check the access level of drafts created through the API in restricted communities. The deposit form still pre-fills restricted access, while API clients must set it explicitly.
- Test that community request notifications reach the roles that can act on them. Group recipients expand to individual members. Check custom mail templates against the new community and sub-community request templates, including their Czech translations if used.
- Test e-INFRA login and API clients that send bearer tokens. With the e-INFRA provider enabled, bearer JWTs that fail e-INFRA validation now return HTTP 403 even on public endpoints.
- Test DOI registration for public records and restricted records. Restricted records are excluded from DOI registration. If DataCite reports that a DOI already exists, the provider now updates it.
- Update custom harvest permissions that reference the removed `oai-harvest-access` permission and verify that harvest managers can access the harvest configuration. For RDM models, use a publishing harvest configuration because `publish=False` raises an error.
- Test an OAI-PMH harvest that includes source updates and deletions. Updates edit, update and publish a draft. Source deletions create tombstones, locally deleted records are restored on subsequent harvests, and the harvester strips `parent.communities` before saving. The harvester continues after a record fails. Enable file harvesting explicitly if you use it.
- Review PID lookups that need pending or otherwise unregistered identifiers. PID resolution now defaults to registered PIDs. Check any assumptions about batch size in custom indexing jobs. `INDEXER_BULK_INDEX_MAX_ITEMS` defaults to 1,000 items per task.
- Verify custom vocabulary integrations. SKOS `exactMatch` and `broadMatch` mappings take precedence over matching `props`, such as `props.datacite`. ROR affiliation and funder imports now update existing items.

</MigrationSteps>

**2. Replace the minio S3 service with RustFS**

The `minio/minio` image can no longer be pulled from Docker Hub. RustFS does not create buckets, so a one-shot `s3-init` service creates the `default` bucket; without it uploads fail with `NoSuchBucket`. In `docker/docker-compose.yml`, replace the `s3` service with:

```yaml filename="docker/docker-compose.yml"
  s3:
    image: rustfs/rustfs:1.0.0
    restart: "unless-stopped"
    environment:
      RUSTFS_ACCESS_KEY: ${INVENIO_S3_ACCESS_KEY}
      RUSTFS_SECRET_KEY: ${INVENIO_S3_SECRET_KEY}
      RUSTFS_ADDRESS: "0.0.0.0:9000"
      RUSTFS_CONSOLE_ENABLE: "true"
      RUSTFS_CONSOLE_ADDRESS: "0.0.0.0:9001"
      RUSTFS_VOLUMES: "/data"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/health"]
      interval: 10s
      timeout: 5s
      retries: 6
    ports:
      - "${INVENIO_S3_HOST}:${INVENIO_S3_PORT}:9000"
      - "${INVENIO_S3_HOST}:${INVENIO_S3_PORT1}:9001"
  s3-init:
    image: rustfs/rustfs:1.0.0
    restart: "no"
    depends_on:
      s3:
        condition: service_healthy
    environment:
      S3_ACCESS_KEY: ${INVENIO_S3_ACCESS_KEY}
      S3_SECRET_KEY: ${INVENIO_S3_SECRET_KEY}
    entrypoint:
      - sh
      - -c
      - >-
        curl -sf --aws-sigv4 "aws:amz:us-east-1:s3" --user "$$S3_ACCESS_KEY:$$S3_SECRET_KEY"
        -X PUT http://s3:9000/default -o /dev/null && echo "bucket default ready"
```

Then recreate the services with `./run.sh services stop` and `./run.sh services start`. Files stored by the old minio service are not copied to RustFS; on a local development instance, `./run.sh reset` brings the database and the storage back in line. See [S3 storage bucket](/installation/run_instance#s3-storage-bucket).

**3. Add the workflow, request and community presets to each model**

Without these presets drafts get no workflow and submitting a draft to a community (`PUT /api/<model>/<id>/draft/review`) returns 403. Skip this for models with the `empty` base model. In `models/<model_name>/model.py`, add the imports and append the presets after the base preset:

```python filename="models/<model_name>/model.py"
from oarepo_communities.model.presets import communities_preset
from oarepo_requests.model.presets.requests import requests_preset
from oarepo_workflows.model.presets import workflows_preset

datasets_model = model(
    "datasets",
    ...
    presets=[
        rdm_complete_preset,
        workflows_preset,
        requests_preset,
        communities_preset,
    ],
    ...
)
```

See [Simplified workflows](/customize/workflows/simplified) for how these presets are used.

**4. Move the sidebar partial to the model's template folder**

Before #42, `nrp-model-copier` generated the sidebar at `ui/<model_name>/templates/semantic-ui/<base_model>/record_detail/record_sidebar.html` (for example `.../semantic-ui/rdm_complete/record_detail/record_sidebar.html`). oarepo-ui only includes `<model_name>/record_detail/record_sidebar.html`, so the file was ignored and the default sidebar was rendered. Move it:

```bash
mv ui/<model_name>/templates/semantic-ui/<base_model>/record_detail/record_sidebar.html \
   ui/<model_name>/templates/semantic-ui/<model_name>/record_detail/record_sidebar.html
```

Once the partial is in place, `OAREPO_UI_SIDEBAR_TEMPLATES` no longer applies to the model, see [Add a sidebar widget](/customize/model_ui/detail#3-add-a-sidebar-widget). For a model with the `empty` base model, also remove the `model_type ~ "/record_detail/record_sidebar.html"` entry from the `record_sidebar` include in `ui/<model_name>/templates/semantic-ui/<model_name>/record_detail.html`; `model_type` is not defined there.

Delete `record_detail/banners.html` if present (see step 1).

**5. `oarepo-app` dependency**

Before #38, `nrp-app-copier` generates the dependency `oarepo-app[ccmm,production]>=6.3.0,<7.0.0`. With #38, new repositories are generated with `oarepo-app[ccmm-development,development]>=7.0.3,<8.0.0` instead, because the `production` extra of `oarepo-app` 6.x pins `oarepo-ui` exactly. For moving an existing repository to `oarepo-app` 7.x, see the [oarepo-app changelog](https://github.com/oarepo/oarepo-app/blob/rdm-14/CHANGELOG.md).

**3. Review behavioral changes and new features**

The upgrade introduces several behavioral changes that may affect your repository:

- **RDM file service configs now apply.** Models using the RDM preset now use `RDMFileService` and `RDMFileServiceConfig` (oarepo-rdm 8.1.0) instead of the base `FileService`. This means RDM file-related configuration — such as `RDM_RECORDS_MAX_FILES_COUNT` (file count limit) — is now enforced. If your repository previously had no file count limits, review the [RDM file config defaults](https://github.com/inveniosoftware/invenio-rdm-records/blob/v32.0.1/invenio_rdm_records/config.py#L872) and adjust if needed.

- **PID/DOI field in the deposit form.** The "General information" section of the deposit form now includes a PID/DOI field (via `RDMPIDsConfigComponent`, oarepo-rdm 8.1.0). The field appears when DOI providers are configured. To disable it, either don't configure DOI providers or override the `PIDField` overridable component in your model's deposit form.

- **Export sidebar filters by `display`.** The export sidebar now only shows exporters where `display=True` (oarepo-ui 13.2.3). The `Export` dataclass defaults `display=True`, so most exports are unaffected. But exports registered with `display=False` (e.g., OAI-only exports) are no longer visible in the UI. To show an export, set `display=True` on the `Export` instance or `AddMetadataExport` customization in your model definition.

- **ZIP content previewing** (invenio-app-rdm 14.0.0rc2). ZIP files can now be browsed and their contents previewed inline. Enabled by default; controlled by `PREVIEWABLE_ZIP_PREVIEWER_NATIVE_EXTENSIONS` (default `["zip"]`). No action needed unless you want to disable it.

- **`/uploads/new` model selection page** (oarepo-rdm 8.1.0). The `/uploads/new` route now shows a model selection page when multiple models exist, or redirects directly when only one model exists. Additive; no action needed.

- **RDM-specific behaviour moved out of `RecordsUIResource`** (oarepo-ui 13.0+). RDM-specific behaviour (default `files.enabled`, `pids` initialisation, `APP_RDM_DEPOSIT_FORM_DEFAULTS`, parent-DOI injection for preview, and DOI-required checks) was removed from the base `RecordsUIResource` in `oarepo-ui` and moved into separate UI components that ship with `oarepo-rdm`: `FilesEnabledComponent`, `EmptyRecordPidsComponent`, `DepositFormDefaultsComponent`, `InjectParentDoiComponent`, `DoiRequiredComponent`, and `RDMPIDsConfigComponent`. If your UI resource and config inherit directly from the generic `RecordsUIResource` / `RecordsUIResourceConfig` (in `oarepo_ui.resources.records`), the new-record form will silently lose default files/PIDs/DOI handling — you must switch your base class. Edit `ui/<model_name>/__init__.py` (for example, `ui/datasets/__init__.py`).

    **For a CCMM-based model** — inherit from `CCMMRecordsUIResourceConfig` and `CCMMRecordsUIResource`, imported from:

    - `from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig`
    - `from ccmm_invenio.ui.resource import CCMMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig
    from ccmm_invenio.ui.resource import CCMMRecordsUIResource

    class DatasetsUIResourceConfig(CCMMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(CCMMRecordsUIResource):
        pass
    ```

    **For a plain RDM-based model** — inherit from `RDMRecordsUIResourceConfig` and `RDMRecordsUIResource`, imported from:

    - `from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig`
    - `from oarepo_rdm.ui.resource import RDMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig
    from oarepo_rdm.ui.resource import RDMRecordsUIResource

    class DatasetsUIResourceConfig(RDMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RDMRecordsUIResource):
        pass
    ```

    If you compose `components` in your config, keep using `*<NewBase>.components` so the new RDM components are included.

- **Search app: default two-column layout** (oarepo-ui 13.0+, [PR #460](https://github.com/oarepo/oarepo-ui/pull/460)). The default search app layout changed for repositories whose search bar lives **in the content area** (not in the page header). The page is now rendered as a two-column layout: facets on the left, results on the right, with the search bar sitting in the right-hand column. If your repository keeps the search bar in the page header (Invenio's default), the rendered page is unchanged and there is nothing to do.

    **Old layout (search bar in content):**

    ![Old search layout](https://github.com/user-attachments/assets/602eb5c9-a41a-4350-9cc3-7b302b9d5c3b)

    Several exported search components were renamed or removed: `ActiveFiltersElement` → `ActiveFilters`, `SearchAppResultOptions` → `ResultOptions`, `SearchAppSort` → `Sort`; `SearchAppLayoutWithSearchbarHOC` and `SearchAppResultViewWithSearchbar` were removed (use `SearchAppLayout` directly).     # Before
    ```python
    url = invenio_url_for("vocabularies.search", type="languages", _external=True)
    api = model.api_url("search", type=alias, _external=True)

    # After
    url = invenio_url_for("vocabularies.search", type="languages")
    api = model.api_url("search", type=alias)
    ```

**4. Review community permission exception handling**

From `oarepo-communities` 8.1.3 (shipped with `oarepo-app` 5.0.0) and 9.0.0 (shipped with `oarepo-app` 6.2.0), the community permission generators no longer raise `MissingCommunitiesError` or `MissingDefaultCommunityError` — they return an empty list instead. Both exception classes are deprecated — their constructors emit a `DeprecationWarning`.

If your code catches these exceptions, that branch is now dead code. Review and update it:

```python
# These are deprecated and no longer raised by the community permission
# generators (OARepoCommunityRoles etc. return [] instead).
from oarepo_communities.errors import (
    MissingCommunitiesError,        # deprecated
    MissingDefaultCommunityError,   # deprecated
)

# Any branch like this is now dead code:
#     except MissingCommunitiesError: ...
# Handle the empty-list case directly instead.
```

Standard `nrp-app-copier` generated repositories do not catch these exceptions, so no action is needed for them.
