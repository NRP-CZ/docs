**1. Replace removed oarepo-ui code**

Find usages in your repository:

```bash
grep -rnE 'RecordSharing|record[-_]sharing|AccessRightField|FilesField|FileUploadWrapper|FileEditWrapper|(Upload|Edit|Delete)FileButton|Histogram|@oarepo/file-manager' \
  --include='*.html' --include='*.jinja' --include='*.js' --include='*.jsx' \
  --exclude-dir=.venv --exclude-dir=node_modules .
find . -path '*/record_detail/banners.html' -not -path './.venv/*'
```

| Removed | Replacement |
|---------|-------------|
| `RecordSharing.jinja`, `record-sharing.js` | InvenioRDM's own share button on the record landing page |
| `AccessRightField` from `@js/oarepo_ui` | `AccessRightField` from `@js/invenio_rdm_records`, see [AccessRightField](/customize/model_ui/deposit_components#accessrightfield) |
| `FilesField` and its parts (`FileUploadWrapper`, `UploadFileButton`, …) | `FileUploader` or `UppyUploader` from `@js/invenio_rdm_records`, see [File Upload Components](/customize/model_ui/deposit_components#file-upload-components) |
| `Histogram`, `HistogramWSlider`, `Slider` from `search/histogram` | None |
| `record_detail/banners.html` partial | None; it was never rendered. Delete the file. See [Record landing page](/customize/model_ui/detail) |

**2. Replace the minio S3 service with RustFS**

The `minio/minio` image can no longer be pulled from Docker Hub. RustFS does not create buckets, so a one-shot `s3-init` service creates the `default` bucket; without it uploads fail with `NoSuchBucket`. In `docker/docker-compose.yml`, replace the `s3` service with:

```yaml filename="docker/docker-compose.yml"
  s3:
    image: rustfs/rustfs:1.0.0
    restart: "unless-stopped"
    environment:
      RUSTFS_ACCESS_KEY: ${INVENIO_S3_ACCESS_KEY}
      RUSTFS_SECRET_KEY: ${INVENIO_S3_SECRET_KEY}
      RUSTFS_ADDRESS: "0.0.0.0:9000"
      RUSTFS_CONSOLE_ENABLE: "true"
      RUSTFS_CONSOLE_ADDRESS: "0.0.0.0:9001"
      RUSTFS_VOLUMES: "/data"
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/health"]
      interval: 10s
      timeout: 5s
      retries: 6
    ports:
      - "${INVENIO_S3_HOST}:${INVENIO_S3_PORT}:9000"
      - "${INVENIO_S3_HOST}:${INVENIO_S3_PORT1}:9001"
  s3-init:
    image: rustfs/rustfs:1.0.0
    restart: "no"
    depends_on:
      s3:
        condition: service_healthy
    environment:
      S3_ACCESS_KEY: ${INVENIO_S3_ACCESS_KEY}
      S3_SECRET_KEY: ${INVENIO_S3_SECRET_KEY}
    entrypoint:
      - sh
      - -c
      - >-
        curl -sf --aws-sigv4 "aws:amz:us-east-1:s3" --user "$$S3_ACCESS_KEY:$$S3_SECRET_KEY"
        -X PUT http://s3:9000/default -o /dev/null && echo "bucket default ready"
```

Then run `./run.sh services stop` and `./run.sh services start`. Files stored by minio are not copied to RustFS; on a local instance, `./run.sh reset` brings the database and storage back in line. See [S3 storage bucket](/installation/run_instance#s3-storage-bucket).

**3. Add the workflow, request and community presets to each model**

Without these presets, drafts get no workflow and submitting a draft to a community returns 403. Skip this for models with the `empty` base model.

```python filename="models/<model_name>/model.py"
from oarepo_communities.model.presets import communities_preset
from oarepo_requests.model.presets.requests import requests_preset
from oarepo_workflows.model.presets import workflows_preset

datasets_model = model(
    "datasets",
    ...
    presets=[
        rdm_complete_preset,
        workflows_preset,
        requests_preset,
        communities_preset,
    ],
    ...
)
```

See [Simplified workflows](/customize/workflows/simplified).

**4. Configure the record detail sidebar in `invenio.cfg`**

The sidebar is a list of boxes, each rendered by its own small template. Configure the list with `config.configure_detail_sidebar` in `invenio.cfg`, instead of overriding the whole sidebar template.

Older `nrp-model-copier` versions generated `ui/<model_name>/templates/semantic-ui/<base_model>/record_detail/record_sidebar.html`. oarepo-ui never rendered it, so delete it. Don't move it to the model's folder: there it would replace the whole sidebar, and `configure_detail_sidebar` would stop working for the model.

To add a box, write a template that renders just that box and register it under a name. Call `configure_detail_sidebar` after `configure_ui` and `configure_ark`, which set up the default boxes:

```python filename="invenio.cfg"
config.configure_detail_sidebar(
    templates={
        # a new box, appended at the end
        "sample_history": "mymodel/record_detail/side_bar/sample_history.html",
        # replace the template of an existing box
        "licenses": "myrepo/records/details/side_bar/licenses.html",
    },
    move=["sample_history after details"],
    remove=["keywords_subjects"],
)
```

See the [`configure_detail_sidebar` reference](https://oarepo.github.io/oarepo-config/reference/index.html#oarepo_config.configure_detail_sidebar) for the names of the built-in boxes, reordering, and per-model sidebars.

If you edited the generated `record_sidebar.html`, move those changes to `configure_detail_sidebar`. For a model with the `empty` base model, also remove the `model_type ~ "/record_detail/record_sidebar.html"` entry from the `record_sidebar` include in `record_detail.html`.

dependencies = [

**6. e-INFRA login**

The synchronization with Perun is now one-way: Perun groups are still propagated to the repository, but community roles set in the repository are not propagated to Perun, and e-mail notifications are sent by the repository. Remove Perun synchronization tasks from your Celery beat schedule if you added them.

To let every e-INFRA eligible user (students, teachers and scientists of the academy of sciences) deposit records, set:

```python filename="invenio.cfg"
from oarepo_oidc_einfra.remote import einfra_eligible_parser_factory
config.configure_einfra_oidc(entitlements_parser=einfra_eligible_parser_factory())
```

**7. Vocabularies**

- Replace `VocabularySelectField`, `LocalVocabularySelectField`, `VocabularyTreeSelectField`, `VocabularyRemoteSelectField` and `VocabularyPickerField` with `VocabularyField` in your deposit forms.
- Administrators can now create and update vocabulary items. Set `VOCABULARIES_PERMISSIONS_POLICY` if you need different permissions.
- The fixture loader now also loads `<model-code>.yaml`, `.json` or `.jsonl` files from `app_data`. Make sure such files contain data you want loaded.

Vocabulary indices have a new SKOS mapping section, so they must be rebuilt (step 15); otherwise creating vocabulary items fails.

**8. Update custom UI code that uses changed oarepo-ui APIs**

Generated model UI needs no change. To find custom code that does, run:

```bash
grep -rnE 'OAREPO_UI_DRAFT_ACTIONS|(record_detail|deposit_edit|deposit_create)_permissions|config\.permissions|filesLocked|images/identifiers|PublishButton|permissions\??\.can_(update|delete|read_files|update_files)\b' \
  --exclude-dir=.venv --exclude-dir=node_modules .
```

| If your code… | Do this |
|---------------|---------|
| sets `OAREPO_UI_DRAFT_ACTIONS` | Move the actions to `OAREPO_UI_RECORD_ACTIONS`. |
| overrides `record_detail_permissions`, `deposit_edit_permissions` or `deposit_create_permissions` in a UI resource config | Delete it. Add any extra action to `OAREPO_UI_RECORD_ACTIONS`. |
| lists its own UI `components` | Include `PermissionsComponent`. |
| reads `can_update`, `can_delete`, `can_read_files` or `can_update_files` in deposit form JS | Use `can_update_draft`, `can_delete_draft`, `can_draft_read_files`, `can_draft_update_files`. |
| reads `config.permissions` or `filesLocked` in deposit form JS | Use `useFormConfig().permissions` and `useFormConfig().filesLocked`. |
| overrides `deposit/form.html` or `deposit_edit/form.html` | Add the `deposits-file-modification` hidden input from [oarepo-ui](https://github.com/oarepo/oarepo-ui/blob/v14.1.0/oarepo_ui/templates/oarepo_ui/deposit/form.html). |
| overrides `<prefix>.TabForm.PublishButton` | Accept the `record` prop. |
| ships icons in `/static/images/identifiers/` | Move them to `/static/images/`. |

**9. Workflow permissions**

If you define your own permission policies, rename `CompositeAndGenerator` to `RequireAll` and `CompositePermissionPolicyMixin` to `BooleanPermissionPolicyMixin`. A policy that uses `RecordOwnerInRecordCommunity` or `RecordOwnerInDefaultRecordCommunity` must inherit from `BooleanPermissionPolicyMixin`.

`CommunityWorkflow` has new defaults. Set explicit role lists if you need the previous behaviour:

- `draft_creation_community_roles`: submitters, curators and owners.
- `read_restricted_community_roles` and `record_manage_community_roles`: curators and owners.

**10. Requests**

- A custom `OAREPO_REQUESTS_DEFAULT_RECEIVER` function is now called with `topic=` instead of `record=`.
- If you override the `publish-draft-request-event.*` e-mail templates, also override `publish-new-version-request-event.*` and `publish-changed-metadata-request-event.*`.
- If you implement custom request types: request types are generic in the topic type, publish request types need a `topic_type` attribute, and `can_create`/`is_applicable_to` must be implemented together.

**11. Community roles**

- **Check your `COMMUNITIES_ROLES` in `invenio.cfg`.** Roles generated by older `nrp-app-copier` give `submitter` `can_manage=True`. Request receivers and notification recipients are now derived from these flags (`can_manage` replaces `manager`, `can_curate` replaces `curator`), so such submitters would receive community submission, inclusion, invitation and membership requests. Set `can_manage=False` on `submitter` and `can_curate=True` on every role that should review submissions.
- Drafts can no longer be created directly in a community; records are added to a community only through review. API clients that create drafts for a restricted community must set the record and file access explicitly.
- Community invitations now use the InvenioRDM UI. If you override the community `details/members/*.html`, `details/settings/base.html` or `details/header.html` templates, compare them with the InvenioRDM templates.

**12. Update `invenio.cfg`**

Import the configuration helpers from `oarepo_config` (skip if you did this in the 6.3.0 migration):

```python filename="invenio.cfg"
import oarepo_config as config
from oarepo_config import CommunityWorkflow, IndividualWorkflow, configure_workflows
```

- Pass `languages=` explicitly to `configure_generic_parameters` and `configure_ui`; the default is now English only. For a Czech repository, use `languages=(("cs", "Czech"),)`.
- Import `is_vedidk`, `ExternalLinkConfig` and similar symbols from `oarepo.initial_rdm_config`.
- `REQUESTS_REVIEWERS_ENABLED` now defaults to `True`.
- The DataCite DOI provider is configured automatically. If you set `RDM_PERSISTENT_IDENTIFIER_PROVIDERS` yourself, name the provider `datacite` so that your settings take precedence. The DOI form default changed from `not_needed` to `no`.
- The legacy `/api/files` endpoint is disabled, and login and signup are limited to 10 requests per minute.

**13. Update model definitions**

- **OAI-PMH.** Import `oai_preset` from `oarepo_rdm.model.presets.oai`.
- **Search customisations.** Search mappings now come from `invenio-rdm-records`. If you use `PatchIndexMapping`, `PatchIndexPropertyMapping` or `SetDefaultSearchFields`, check that the patched fields still exist.
- **Subjects.** Subjects now reference the `subjects` vocabulary. Facets on `metadata.subjects` filter on the vocabulary ID. See [Facet Configuration in Model Schema](/customize/model_backend/search#facet-configuration-in-model-schema).
- **Dates.** `RDMDate.date` now accepts EDTF dates and intervals.
- **Related identifiers (CCMM).** They are now stored in `metadata.related_resources`; `metadata.related_identifiers` is computed. Update imports and API clients.
- **`metadata.yaml`.** Set `model:` on `pid-relation` fields and replace `multilingual-type` with `multilingual`.

**14. Exports**

- The `citation` export was replaced by `bibliography`.
- DataCite is exported as `datacite-json` and `datacite-xml` (for CCMM, these replace `datacite`). CCMM XML is available as `ccmm-xml` and as `ccmm` in OAI-PMH. The `dcat` OAI-PMH format was removed.

Update integrations and OAI-PMH consumers that use the removed formats.

**15. Migrate the database and data, and rebuild the indices**

For a disposable local instance, run `./run.sh reset` and continue with step 17.

<Callout type="warning">
  `./run.sh reset` deletes local data. To keep existing data, back up the database and rehearse the migration on a staging copy.
</Callout>

1. Install the dependencies, rebuild the assets and migrate the database:

   ```bash
   ./run.sh upgrade
   ./run.sh invenio alembic upgrade
   ```

2. Load the subject schemes your records use, for example `./run.sh invenio rdm-records add-to-fixture subjects.FORD`, and wait for the tasks to finish. See [Initial data for vocabularies](/customize/vocabularies/initial_data).
3. Convert legacy subject values in records and drafts to vocabulary references. For CCMM, copy identifiers stored only in `metadata.related_identifiers` to `metadata.related_resources`.
4. Rebuild the indices and wait for the Celery workers to finish. Repositories with legacy CCMM data do this as part of step 16.

   ```bash
   ./run.sh index rebuild
   ```

**16. Migrate existing CCMM vocabularies and records**

Copy [`scripts/migration_vocabs.py`](https://github.com/NRP-CZ/ccmm-invenio/blob/v2.0.2/scripts/migration_vocabs.py) from your `ccmm-invenio` version into your repository and add every CCMM model table to its `TABLES` list. It renames vocabulary types, loads the new vocabularies and converts references in records and drafts.

```bash
./run.sh invenio shell scripts/migration_vocabs.py mark
./run.sh invenio shell scripts/migration_vocabs.py migrate_types
./run.sh invenio shell scripts/migration_vocabs.py load
./run.sh index rebuild         # wait for indexing to finish
./run.sh invenio shell scripts/migration_vocabs.py migrate_data
./run.sh index rebuild         # review "cannot convert" messages, check records
./run.sh invenio shell scripts/migration_vocabs.py remove_deprecated
./run.sh index rebuild
```

- Open and edit existing records and drafts; check search, facets, vocabulary fields and files.
- Submit a draft to a community and publish it; check who receives the request and its notifications.
- Test e-INFRA login, DOI registration and the exports you use.

**3. Review behavioral changes and new features**

The upgrade introduces several behavioral changes that may affect your repository:

- **RDM file service configs now apply.** Models using the RDM preset now use `RDMFileService` and `RDMFileServiceConfig` (oarepo-rdm 8.1.0) instead of the base `FileService`. This means RDM file-related configuration — such as `RDM_RECORDS_MAX_FILES_COUNT` (file count limit) — is now enforced. If your repository previously had no file count limits, review the [RDM file config defaults](https://github.com/inveniosoftware/invenio-rdm-records/blob/v32.0.1/invenio_rdm_records/config.py#L872) and adjust if needed.

- **PID/DOI field in the deposit form.** The "General information" section of the deposit form now includes a PID/DOI field (via `RDMPIDsConfigComponent`, oarepo-rdm 8.1.0). The field appears when DOI providers are configured. To disable it, either don't configure DOI providers or override the `PIDField` overridable component in your model's deposit form.

- **Export sidebar filters by `display`.** The export sidebar now only shows exporters where `display=True` (oarepo-ui 13.2.3). The `Export` dataclass defaults `display=True`, so most exports are unaffected. But exports registered with `display=False` (e.g., OAI-only exports) are no longer visible in the UI. To show an export, set `display=True` on the `Export` instance or `AddMetadataExport` customization in your model definition.

- **ZIP content previewing** (invenio-app-rdm 14.0.0rc2). ZIP files can now be browsed and their contents previewed inline. Enabled by default; controlled by `PREVIEWABLE_ZIP_PREVIEWER_NATIVE_EXTENSIONS` (default `["zip"]`). No action needed unless you want to disable it.

- **`/uploads/new` model selection page** (oarepo-rdm 8.1.0). The `/uploads/new` route now shows a model selection page when multiple models exist, or redirects directly when only one model exists. Additive; no action needed.

- **RDM-specific behaviour moved out of `RecordsUIResource`** (oarepo-ui 13.0+). RDM-specific behaviour (default `files.enabled`, `pids` initialisation, `APP_RDM_DEPOSIT_FORM_DEFAULTS`, parent-DOI injection for preview, and DOI-required checks) was removed from the base `RecordsUIResource` in `oarepo-ui` and moved into separate UI components that ship with `oarepo-rdm`: `FilesEnabledComponent`, `EmptyRecordPidsComponent`, `DepositFormDefaultsComponent`, `InjectParentDoiComponent`, `DoiRequiredComponent`, and `RDMPIDsConfigComponent`. If your UI resource and config inherit directly from the generic `RecordsUIResource` / `RecordsUIResourceConfig` (in `oarepo_ui.resources.records`), the new-record form will silently lose default files/PIDs/DOI handling — you must switch your base class. Edit `ui/<model_name>/__init__.py` (for example, `ui/datasets/__init__.py`).

    **For a CCMM-based model** — inherit from `CCMMRecordsUIResourceConfig` and `CCMMRecordsUIResource`, imported from:

    - `from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig`
    - `from ccmm_invenio.ui.resource import CCMMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig
    from ccmm_invenio.ui.resource import CCMMRecordsUIResource

    class DatasetsUIResourceConfig(CCMMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(CCMMRecordsUIResource):
        pass
    ```

    **For a plain RDM-based model** — inherit from `RDMRecordsUIResourceConfig` and `RDMRecordsUIResource`, imported from:

    - `from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig`
    - `from oarepo_rdm.ui.resource import RDMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig
    from oarepo_rdm.ui.resource import RDMRecordsUIResource

    class DatasetsUIResourceConfig(RDMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RDMRecordsUIResource):
        pass
    ```

    If you compose `components` in your config, keep using `*<NewBase>.components` so the new RDM components are included.

- **Search app: default two-column layout** (oarepo-ui 13.0+, [PR #460](https://github.com/oarepo/oarepo-ui/pull/460)). The default search app layout changed for repositories whose search bar lives **in the content area** (not in the page header). The page is now rendered as a two-column layout: facets on the left, results on the right, with the search bar sitting in the right-hand column. If your repository keeps the search bar in the page header (Invenio's default), the rendered page is unchanged and there is nothing to do.

    ![New search layout](https://github.com/user-attachments/assets/e305b943-10b1-4365-802f-6db247ca553c)

    Several exported search components were renamed or removed: `ActiveFiltersElement` → `ActiveFilters`, `SearchAppResultOptions` → `ResultOptions`, `SearchAppSort` → `Sort`; `SearchAppLayoutWithSearchbarHOC` and `SearchAppResultViewWithSearchbar` were removed (use `SearchAppLayout` directly). These changes only affect custom search code that imports the old component names directly — the copier-generated `search/index.js` is unaffected because it only uses `parseSearchAppConfigs` and `createSearchAppsInit`, which exist in both versions. A `Scroll to top` button is now rendered by default; if you do not want it, hide it via CSS (`#scroll-to-top-button { display: none; }`).

- **`invenio_url_for` and `Model.api_url` no longer accept `_external=True`** (oarepo-runtime 4.0.0+). Both helpers now **always** return an absolute (external) URL. Passing `_external=True` is no longer accepted and will raise (`Model.api_url` calls `invenio_url_for` under the hood and fails for the same reason). Drop `_external=True` from these calls — the returned URL is already absolute.

    ```python
    # Before
    url = invenio_url_for("vocabularies.search", type="languages", _external=True)
    api = model.api_url("search", type=alias, _external=True)

    # After
    url = invenio_url_for("vocabularies.search", type="languages")
    api = model.api_url("search", type=alias)
    ```

**4. Review community permission exception handling**

From `oarepo-communities` 8.1.3 (shipped with `oarepo-app` 5.0.0) and 9.0.0 (shipped with `oarepo-app` 6.2.0), the community permission generators no longer raise `MissingCommunitiesError` or `MissingDefaultCommunityError` — they return an empty list instead. Both exception classes are deprecated — their constructors emit a `DeprecationWarning`.

If your code catches these exceptions, that branch is now dead code. Review and update it:

```python
# These are deprecated and no longer raised by the community permission
# generators (OARepoCommunityRoles etc. return [] instead).
from oarepo_communities.errors import (
    MissingCommunitiesError,        # deprecated
    MissingDefaultCommunityError,   # deprecated
)

# Any branch like this is now dead code:
#     except MissingCommunitiesError: ...
# Handle the empty-list case directly instead.
```

Standard `nrp-app-copier` generated repositories do not catch these exceptions, so no action is needed for them.

**5. Consider migrating to the simplified workflows**

See [simplified workflows](/customize/workflows/simplified) for a more streamlined approach to workflow configuration.

</MigrationSteps>

<MigrationHeader
  date="2026-04-15"
  title="Models moved under models/ folder"
  prHref="https://github.com/oarepo/nrp-model-copier/pull/34"
  versionBadge="nrp-model-copier"
/>

The `model create` command now places the backend part of new models inside a `models/` folder
(e.g. `models/datasets/`) instead of creating them as top-level directories (e.g. `datasets/`).
This keeps the repository structure cleaner as the number of models grows. New models are placed under `models/` automatically, so no action is needed for them — the steps below only apply to existing models that still live at the repository root.

<Callout type="info">
Existing repositories with models already at the top level will continue to work.
However, for a consistent folder structure we recommend moving existing models into `models/` as well.
</Callout>

<MigrationAffected>

| Affected | Not affected |
|----------|--------------|
| Repositories with models created at the top level before 2026-04-15 | Newly created repositories |
| Repositories adding new models alongside existing top-level models | Repositories with no models yet |

</MigrationAffected>

<MigrationSteps>

**1. Move existing top-level models into `models/`**

```bash
mv datasets models/
```

Repeat for every model that currently lives at the repository root.

**2. Update `invenio.cfg`**

Update the model import paths. For example, if you have a model called `datasets`:

```python filename="invenio.cfg"
# Before
from datasets import datasets_model
datasets_model.register()

# After
from models.datasets import datasets_model
datasets_model.register()
```

**3. Update `pyproject.toml`**

In the `module-name` section of `pyproject.toml`, remove the entry for the model folder you just moved
(e.g. remove `datasets`). The model is now discovered from `models/` automatically.

</MigrationSteps>
