# Migrations & Updates

<MigrationHeader
  date="2026-09-29"
  title="oarepo-app 6.x → 7.0.3"
  versionBadge="oarepo-app ≥ 7.0.3"
/>

`oarepo-app` 7 transitions the pinned stack from the InvenioRDM 14 **release candidates** to the **final** v14 releases (`invenio-app-rdm 14.0.0rc4 → 14.0.0`, `invenio-rdm-records → 32.2.1`, `invenio-communities → 28.x`) and lands a major-version cascade across the `oarepo-*` packages (`oarepo-ui` 11→13.5.3, `oarepo-vocabularies` 7→10.2.1, `oarepo-communities` 9→12.1.2, `oarepo-theme` 4→6, `oarepo-dashboard` 6→8, `oarepo-requests` 7→9.5.2, `oarepo-rdm` 6→8.6.1, `oarepo-runtime` 5→7.7.0, `oarepo-model` 3→5.4.1, `oarepo-oidc-einfra` 5→8.0.1). For the full list of package changes see the [oarepo-app v7.0.0rc1 and later release notes](https://github.com/oarepo/oarepo-app/releases).

Most major bumps are mechanical dependency re-pins, but four areas contain **genuine breaking changes** that custom UI code may hit:

1. The **deposit-form overridable component IDs** were renamed upstream ([invenio-rdm-records PR #2101](https://github.com/inveniosoftware/invenio-rdm-records/pull/2101), shipped in invenio-rdm-records 29.x, so it affects even 6.4.x installations on older pins).
2. **oarepo-vocabularies v10 removed every deposit-form vocabulary React component** in favour of a single generic `VocabularyField`, so any JS importing the old `@js/oarepo_vocabularies` form components breaks at build time.
3. **oarepo-communities v12 removed its custom invitation/membership UI**, falling back to the upstream invenio-communities UI.
4. **oarepo-ui v12/v13 unified permission actions** (`OAREPO_UI_DRAFT_ACTIONS` and per-page permission classvars were removed, `permissions` moved out of `form_config`) and now requires **jinjax ≥ 0.64**, which breaks custom `Catalog` subclasses that skip `super().__init__()`.

React did **not** move (`react@^16.13`, `semantic-ui-react@^2.1`, Formik `^2`), and `oarepo-theme` 4→6 is a pure `pyproject.toml` bump with no template/LESS/webpack change.

<MigrationAffected>

| Affected | Not affected |
|----------|--------------|
| Repositories on `oarepo-app < 7.0.0` upgrading to 7.0.x | Repositories already on `oarepo-app >= 7.0.3` |
| Repositories overriding deposit-form components by their overridable IDs in `overridableRegistry/mapping.js` | Standard `nrp-app-copier` generated repositories that use only model-generated components (the copier templates use model-local `buildUID(prefix, Name)` IDs, which are unchanged) |
| Repositories importing `VocabularySelectField`, `VocabularyRemoteSelectField`, `VocabularyPickerField`, `VocabularyTreeSelectField`, `LocalVocabularySelectField` or related helpers from `@js/oarepo_vocabularies` | Repositories that only set `vocabulary` types in `metadata.yaml` — those already render through the generic `VocabularyField` |
| Repositories importing `CommunityInvitationsModal` (or its template/overridable overrides) from oarepo-communities | Repositories that never customized the invitations UI |
| Repositories subclassing oarepo-ui `UIResourceComponent` hooks (`before_ui_detail`, `before_ui_edit`, `before_ui_create`) or reading `permissions` from `form_config` | Repositories using unmodified resource components |
| Repositories with a custom JinjaX `Catalog` subclass that overrides `__init__` without calling `super().__init__()` | Standard jinjax usage via components |

</MigrationAffected>

<MigrationSteps>

**1. Update `pyproject.toml`**

Bump the `oarepo-app` dependency and let it pull the final RDM 14 stack:

```toml filename="pyproject.toml"
# Before
dependencies = [
    "oarepo-app[production,ccmm]==6.4.0rc5",   # or any 6.x
]

# After
dependencies = [
    "oarepo-app[production,ccmm]==7.0.3",
]
```

Then reinstall and rebuild:

```bash
./run.sh upgrade                   # reinstall with the new pins
./run.sh invenio alembic upgrade   # database schema migrations (rdm-records 32.x, communities 28.x, requests, oidc-einfra changed schemas)
./run.sh index rebuild             # drop, recreate and reindex OpenSearch (mappings changed)
./run.sh run                       # let Celery workers process the reindex queue
```

<Callout type="warning">
As with the 6.3.0 migration, the production Alembic procedure is still work in progress — test it against a database copy first. Local development can use `./run.sh reset` instead (wipes data).
</Callout>

**2. Update renamed upstream configuration variables**

If you set any of these in `invenio.cfg`, rename them (see the official [v13→v14 upgrade guide](https://inveniordm.docs.cern.ch/releases/v14/upgrade-v14.0/)):

- `COMMUNITIES_SHOW_BROWSE_MENU_ENTRY` → `COMMUNITIES_COLLECTIONS_ENABLED`
- `WSGI_PROXIES = N` was removed → use `PROXYFIX_CONFIG = {"x_for": ..., "x_proto": ...}` matching your reverse-proxy setup
- `COMMUNITIES_GROUPS_ENABLED` (deprecated) → `USERS_RESOURCES_GROUPS_ENABLED`
- If you rely on `invenio-cli run --host/--port` to set `SITE_UI_URL`/`SITE_API_URL` — it no longer does; set them explicitly in `invenio.cfg` (e.g. `https://127.0.0.1:5000` and `https://127.0.0.1:5000/api`).

**3. Rewrite deposit-form overridable IDs (only if you override by ID)**

Upstream renamed the deposit form's overridable component IDs to a uniform `InvenioRdmRecords.DepositForm.<Field>[.<sub>]` scheme. Two representative renames:

```jsx filename="assets/js/overridableRegistry/mapping.js"
// Before
export const overriddenComponents = {
  "InvenioRdmRecords.DatesField.DateTextField.Container": MyDateField,
  "InvenioRDMRecords.CreatibutorsModal.FullNameField.container": MyFullName,
};

// After
export const overriddenComponents = {
  "InvenioRdmRecords.DepositForm.DatesField.DateField": MyDateField,
  "InvenioRdmRecords.DepositForm.CreatibutorsModal.FullNameField": MyFullName,
};
```

Check your mapping file against the [full list of ID changes](https://github.com/inveniosoftware/invenio-rdm-records/pull/2101/files). Note the behavior change that came with the refactor: every field is wrapped by `createCommonFieldDepositComponent`, so passing `hidden: true` now suppresses rendering — but Formik still submits the stored initial value. `hidden` is not the same as clearing a field.

Model-generated oarepo components (CCMM sections) use their own `buildUID(overridableIdPrefix, "Name")` IDs and are **not affected** by this upstream rename.

**4. Update custom-field widget props**

If you developed custom React widgets or override built-in ones with `parametrize`, rename the deprecated props (old names still work for now but will be removed):

```jsx
// Before
parametrize(TitlesField, { icon: "barcode", description: "Describe your resource" })

// After
parametrize(TitlesField, { labelIcon: "barcode", helpText: "Describe your resource" })
```

**5. Migrate removed vocabulary form components (only if you imported them)**

oarepo-vocabularies v10 removed all deposit-form React components:
`LocalVocabularySelectField`, `VocabularySelectField`, `VocabularyRemoteSelectField` (with its modal and search-app pieces), `VocabularyPickerField`, `VocabularyTreeSelectField` (+ `HierarchyColumn`, `TreeSelectFieldModal`, `TreeSelectValues`), `SelectedVocabularyValues`, `OptionsLoadingSkeleton`, and the Python `oarepo_vocabularies/ui/resources/components/deposit.py`.

The replacement is the single generic `VocabularyField`, which is already what model-generated forms use for `vocabulary: <name>` types via `useFieldData()` / `getFieldData()` (labels, help text and required flags come from `metadata.yaml`; initial options resolve from the record's UI serialization as `{id, title_l10n}` pairs). If you imported the removed components directly, migrate to `VocabularyField` — see, for example, how the generated `forms/index.js` uses it. Webpack entry points and aliases (`@js/oarepo_vocabularies`, `@translations/oarepo_vocabularies_ui`) are unchanged.

**6. Remove oarepo-communities invitation UI references (only if you customized it)**

oarepo-communities v12 removed the custom invitation/membership UI: the `CommunityInvitationsModal` React component (with `serializeMembers` / `findAndValidateEmails` helpers), the 12 `UIComponentOverride` registrations on the `invenio_communities.members` / `invenio_communities.invitations` bundles (`InvenioCommunities.CommunityMembersSearch.InvitationsEmptyResults|InvitationsResultsContainer|InvitationsSearchLayout|ManagerEmptyResults|ManagerMembersResultsContainer|ManagerSearchLayout` and `InvitationsModal.container`), and the template overrides `details/members/base.html`, `details/members/invitations.html` and `details/settings/base.html`. The pages now silently fall back to the upstream invenio-communities UI.

Also remove, if present:

- any `@js/oarepo_communities/components/CommunityInvitationsModal` import,
- the `RDM_RECORDS_COMMUNITY_RECORDS_SERVICE_CLASS` config variable and any import of `oarepo_communities.services.community_records.CommunityRecordsService` (both removed; functionality superseded by upstream community-records machinery),
- any reference to `oarepo_communities.config.community_members_recipient` in notification configuration (replaced by `CommunityRoleEmailRecipient` / `CommunityRecipient` keyed to the request type's `needs_context["community_roles"]`). Note that v12.1.2 also replaces hardcoded `manager`/`curator` role names on upstream request types with the roles configured in `COMMUNITIES_ROLES` (`can_manage` / `can_curate`) — if you renamed community roles, requests now notify/notify-only the right recipients.

Behavior change worth knowing even with no custom code: when a community review is declined/expired/cancelled, a fresh `community-submission` request is now auto-created and the draft returns to `draft_with_review` (the "submit for review" button reappears), instead of the draft staying in the declined/expired state. UI tests that assert the upstream declined-state behavior will break.

Additive goodies in v12 you may want to opt into: the **collections UI** (`/collections` routes with browse/detail pages, controlled by `INVENIO_COLLECTIONS_COMMUNITY_SLUG` / `INVENIO_COLLECTIONS_UI_URL_PREFIX`) and a **sub-community creation button** injected via a new `details/header.html` override — if your site also overrides that template's `subheader_buttons` block, reconcile the two overrides.

**7. Update custom `UIResourceComponent` hooks and permission reads (only if you subclassed them)**

oarepo-ui 12/13 unified record/draft permission actions ([PR #480](https://github.com/oarepo/oarepo-ui/pull/480)):

- `OAREPO_UI_DRAFT_ACTIONS` and `ext.draft_actions` were removed — `OAREPO_UI_RECORD_ACTIONS` is the single action set, and draft actions map to **distinct** flags (`can_delete_draft` is no longer aliased onto `can_delete`). Update templates/components that relied on the old remapping.
- `PermissionsComponent.form_config()` was removed: `permissions` no longer appears inside `form_config`. On the Python side it is injected into `extra_context` / `render_kwargs`; on the frontend `DepositFormApp.jsx` reads top-level `props.permissions` instead of `props.config.permissions`.
- `RecordsUIResourceConfig.record_detail_permissions` / `deposit_edit_permissions` / `deposit_create_permissions` classvars and `resource.get_record_permissions()` were removed.
- `UIResourceComponent.before_ui_detail` / `before_ui_edit` / `before_ui_create` gained an explicit `render_kwargs: dict` parameter — subclasses overriding these hooks must accept it.
- `FilesLockedComponent` now derives the locked state from the draft file bucket lock (`draft.files.bucket.locked`) instead of `can_update_files` / `record.is_published`, and writes `render_kwargs["files_locked"]` (previously `form_config["filesLocked"]`). The deposit page template gained a `deposits-file-modification` hidden input consumed by `parseFormAppConfig()` as `fileModification`.

**8. Fix custom JinjaX `Catalog` subclasses for jinjax ≥ 0.64 (only if you have one)**

jinjax 0.61 introduced deferred asset injection; 0.64 (required by oarepo-ui 13) makes it mandatory. If you subclass `jinjax.Catalog` and override `__init__` without calling `super().__init__()` (as `oarepo_ui/templating/catalog.py` does), you must set these attributes or `irender` raises `AttributeError`:

```python
# inside your Catalog.__init__
self.fingerprint = False
self._assets_placeholder = f"@@jinjax_assets_{self._key}@@"
self._emit_assets_later = False
```

Also note jinjax 0.61 stopped sorting the HTML `class` attribute — snapshot tests that assume sorted classes may need updating.

**9. Check search-component imports (only if you use them directly)**

From oarepo-ui v11 (already shipped with oarepo-app 6.0, but re-verify): `ActiveFiltersElement` → `ActiveFilters`, `SearchAppResultOptions` → `ResultOptions`, `SearchAppSort` → `Sort`; `SearchAppLayoutWithSearchbar` and `SearchAppResultViewWithSearchbar` were removed (folded into `SearchAppLayout` / `SearchAppResults`). Copier-generated `search/index.js` uses only the stable helpers (`parseSearchAppConfigs`, `createSearchAppsInit`) and is unaffected. The webpack entries are unchanged across v11→v13.5.3.

**10. Reconcile with `oarepo_app.workarounds` (only if you patched fixtures yourself)**

oarepo-app 7 registers `oarepo_app.workarounds` as an `invenio_config.module` entry point. It monkey-patches `invenio_rdm_records.fixtures.vocabularies.VocabulariesFixture.load` and `VocabularyEntry.load` to load fixture vocabularies via a `ThreadPoolExecutor` with bulk indexing, and tunes GC settings at `app_loaded`. If your instance ships its own monkey-patch of the same fixture methods, remove or reconcile it — the built-in patch overwrites `load` unconditionally.

**11. Optional toolchain upgrades**

Nothing forces these, but v14 marked them as the supported defaults:

- **Node.js ≥ 24** (24 or 26 were tested) is now required for building assets.
- **Python 3.14** is required (oarepo-app 6 already required 3.14).
- **rspack** instead of webpack: `WEBPACKEXT_PROJECT = "invenio_assets.webpack:rspack_project"` in `invenio.cfg` (and add rspack to your Dockerfile asset stage).
- **pnpm** instead of npm: `javascript_package_manager = pnpm` in `.invenio` and `WEBPACKEXT_NPM_PKG_CLS = "pynpm:PNPMPackage"` in `invenio.cfg`.

**12. Re-run vocabulary fixtures if you customized them**

The upstream v14 stock vocabularies changed (new/changed entries for `datetypes`, `descriptiontypes`, `licenses`, `relationtypes`, `resourcetypes`, `contributorsroles`, `creatorsroles`, `titletypes`, `removalreasons`; notably the `publication-thesis` entry was merged into `publication-dissertation`). If you have customized vocabulary files under `app_data/vocabularies/`, merge upstream changes into them and update with `invenio rdm-records add-to-fixture <vocabulary>` — details in the official upgrade guide (aligning thesis/dissertation resource types is optional and can be done later).

</MigrationSteps>

```toml filename="pyproject.toml"
dependencies = [
```

The `oarepo[s3,rdm]` line needs no change — its range already covers the `oarepo` version pulled in by the `production` extra. The `production` extra now also includes `oarepo-related-resources`, so that package is installed automatically.

**2. Reinstall and reinitialize the database and index**

The `invenio-rdm-records` major bump changed the database schema and the search mappings, so the database and indices need to be brought in line with the new versions. Follow [Database and index reinitialization](/customize/model_backend/db_update):


The production Alembic migration procedure is still work in progress. See the [`./run.sh` reference](/installation/run_script) for command details.

**3. Review behavioral changes and new features**

The upgrade introduces several behavioral changes that may affect your repository:

- **RDM file service configs now apply.** Models using the RDM preset now use `RDMFileService` and `RDMFileServiceConfig` (oarepo-rdm 8.1.0) instead of the base `FileService`. This means RDM file-related configuration — such as `RDM_RECORDS_MAX_FILES_COUNT` (file count limit) — is now enforced. If your repository previously had no file count limits, review the [RDM file config defaults](https://github.com/inveniosoftware/invenio-rdm-records/blob/v32.0.1/invenio_rdm_records/config.py#L872) and adjust if needed.

- **PID/DOI field in the deposit form.** The "General information" section of the deposit form now includes a PID/DOI field (via `RDMPIDsConfigComponent`, oarepo-rdm 8.1.0). The field appears when DOI providers are configured. To disable it, either don't configure DOI providers or override the `PIDField` overridable component in your model's deposit form.

- **Export sidebar filters by `display`.** The export sidebar now only shows exporters where `display=True` (oarepo-ui 13.2.3). The `Export` dataclass defaults `display=True`, so most exports are unaffected. But exports registered with `display=False` (e.g., OAI-only exports) are no longer visible in the UI. To show an export, set `display=True` on the `Export` instance or `AddMetadataExport` customization in your model definition.

- **ZIP content previewing** (invenio-app-rdm 14.0.0rc2). ZIP files can now be browsed and their contents previewed inline. Enabled by default; controlled by `PREVIEWABLE_ZIP_PREVIEWER_NATIVE_EXTENSIONS` (default `["zip"]`). No action needed unless you want to disable it.

- **`/uploads/new` model selection page** (oarepo-rdm 8.1.0). The `/uploads/new` route now shows a model selection page when multiple models exist, or redirects directly when only one model exists. Additive; no action needed.

- **RDM-specific behaviour moved out of `RecordsUIResource`** (oarepo-ui 13.0+). RDM-specific behaviour (default `files.enabled`, `pids` initialisation, `APP_RDM_DEPOSIT_FORM_DEFAULTS`, parent-DOI injection for preview, and DOI-required checks) was removed from the base `RecordsUIResource` in `oarepo-ui` and moved into separate UI components that ship with `oarepo-rdm`: `FilesEnabledComponent`, `EmptyRecordPidsComponent`, `DepositFormDefaultsComponent`, `InjectParentDoiComponent`, `DoiRequiredComponent`, and `RDMPIDsConfigComponent`. If your UI resource and config inherit directly from the generic `RecordsUIResource` / `RecordsUIResourceConfig` (in `oarepo_ui.resources.records`), the new-record form will silently lose default files/PIDs/DOI handling — you must switch your base class. Edit `ui/<model_name>/__init__.py` (for example, `ui/datasets/__init__.py`).

    **For a CCMM-based model** — inherit from `CCMMRecordsUIResourceConfig` and `CCMMRecordsUIResource`, imported from:

    - `from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig`
    - `from ccmm_invenio.ui.resource import CCMMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from ccmm_invenio.ui.config import CCMMRecordsUIResourceConfig
    from ccmm_invenio.ui.resource import CCMMRecordsUIResource

    class DatasetsUIResourceConfig(CCMMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(CCMMRecordsUIResource):
        pass
    ```

    **For a plain RDM-based model** — inherit from `RDMRecordsUIResourceConfig` and `RDMRecordsUIResource`, imported from:

    - `from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig`
    - `from oarepo_rdm.ui.resource import RDMRecordsUIResource`

    ```python filename="ui/<model_name>/__init__.py"
    # Before
    from oarepo_ui.resources.records.config import RecordsUIResourceConfig
    from oarepo_ui.resources.records.resource import RecordsUIResource

    class DatasetsUIResourceConfig(RecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RecordsUIResource):
        pass

    # After
    from oarepo_rdm.ui.config import RDMRecordsUIResourceConfig
    from oarepo_rdm.ui.resource import RDMRecordsUIResource

    class DatasetsUIResourceConfig(RDMRecordsUIResourceConfig):
        ...

    class DatasetsUIResource(RDMRecordsUIResource):
        pass
    ```

    If you compose `components` in your config, keep using `*<NewBase>.components` so the new RDM components are included.

- **Search app: default two-column layout** (oarepo-ui 13.0+, [PR #460](https://github.com/oarepo/oarepo-ui/pull/460)). The default search app layout changed for repositories whose search bar lives **in the content area** (not in the page header). The page is now rendered as a two-column layout: facets on the left, results on the right, with the search bar sitting in the right-hand column. If your repository keeps the search bar in the page header (Invenio's default), the rendered page is unchanged and there is nothing to do.

    **Old layout (search bar in content):**

    ![Old search layout](https://github.com/user-attachments/assets/602eb5c9-a41a-4350-9cc3-7b302b9d5c3b)

    **New layout (search bar in content):**

    ![New search layout](https://github.com/user-attachments/assets/e305b943-10b1-4365-802f-6db247ca553c)

    Several exported search components were renamed or removed: `ActiveFiltersElement` → `ActiveFilters`, `SearchAppResultOptions` → `ResultOptions`, `SearchAppSort` → `Sort`; `SearchAppLayoutWithSearchbarHOC` and `SearchAppResultViewWithSearchbar` were removed (use `SearchAppLayout` directly). These changes only affect custom search code that imports the old component names directly — the copier-generated `search/index.js` is unaffected because it only uses `parseSearchAppConfigs` and `createSearchAppsInit`, which exist in both versions. A `Scroll to top` button is now rendered by default; if you do not want it, hide it via CSS (`#scroll-to-top-button { display: none; }`).

- **`invenio_url_for` and `Model.api_url` no longer accept `_external=True`** (oarepo-runtime 4.0.0+). Both helpers now **always** return an absolute (external) URL. Passing `_external=True` is no longer accepted and will raise (`Model.api_url` calls `invenio_url_for` under the hood and fails for the same reason). Drop `_external=True` from these calls — the returned URL is already absolute.

    ```python
    # Before
    url = invenio_url_for("vocabularies.search", type="languages", _external=True)
    api = model.api_url("search", type=alias, _external=True)

    # After
    url = invenio_url_for("vocabularies.search", type="languages")
    api = model.api_url("search", type=alias)
    ```

**4. Review community permission exception handling**

From `oarepo-communities` 8.1.3 (shipped with `oarepo-app` 5.0.0) and 9.0.0 (shipped with `oarepo-app` 6.2.0), the community permission generators no longer raise `MissingCommunitiesError` or `MissingDefaultCommunityError` — they return an empty list instead. Both exception classes are deprecated — their constructors emit a `DeprecationWarning`.

If your code catches these exceptions, that branch is now dead code. Review and update it:

```python
# These are deprecated and no longer raised by the community permission
# generators (OARepoCommunityRoles etc. return [] instead).
from oarepo_communities.errors import (
    MissingCommunitiesError,        # deprecated
    MissingDefaultCommunityError,   # deprecated
)

# Any branch like this is now dead code:
#     except MissingCommunitiesError: ...
# Handle the empty-list case directly instead.
```

Standard `nrp-app-copier` generated repositories do not catch these exceptions, so no action is needed for them.

**5. Consider migrating to the simplified workflows**

See [simplified workflows](/customize/workflows/simplified) for a more streamlined approach to workflow configuration.

</MigrationSteps>

<MigrationHeader
  date="2026-04-15"
  title="Models moved under models/ folder"
  prHref="https://github.com/oarepo/nrp-model-copier/pull/34"
  versionBadge="nrp-model-copier"
/>

The `model create` command now places the backend part of new models inside a `models/` folder
(e.g. `models/datasets/`) instead of creating them as top-level directories (e.g. `datasets/`).
This keeps the repository structure cleaner as the number of models grows. New models are placed under `models/` automatically, so no action is needed for them — the steps below only apply to existing models that still live at the repository root.

<Callout type="info">
Existing repositories with models already at the top level will continue to work.
However, for a consistent folder structure we recommend moving existing models into `models/` as well.
</Callout>

<MigrationAffected>

| Affected | Not affected |
|----------|--------------|
| Repositories with models created at the top level before 2026-04-15 | Newly created repositories |
| Repositories adding new models alongside existing top-level models | Repositories with no models yet |

</MigrationAffected>

<MigrationSteps>

**1. Move existing top-level models into `models/`**

```bash
mv datasets models/
```

Repeat for every model that currently lives at the repository root.

**2. Update `invenio.cfg`**

Update the model import paths. For example, if you have a model called `datasets`:

```python filename="invenio.cfg"
# Before
from datasets import datasets_model
datasets_model.register()

# After
from models.datasets import datasets_model
datasets_model.register()
```

**3. Update `pyproject.toml`**

In the `module-name` section of `pyproject.toml`, remove the entry for the model folder you just moved
(e.g. remove `datasets`). The model is now discovered from `models/` automatically.

</MigrationSteps>
